## Context

The only contract is `contracts/fraud/v1/fraud.proto`, consumed by the Go edge (`POST /predict`) and served by the Python fraud service with a pickled handbook model, pandas preprocessing, a thread-pool for native inference and hardcoded handbook customer/terminal blocklists. Protobuf bindings are generated by the devenv `codegen:proto` task into `src/fraud-service/` (Python) and `src/edge/gen/` (Go) and committed. Nothing outside this repository calls either service, and the edge is not deployed by any chart.

Two follow-up changes depend on these contracts: `generate-historical-synthetic-data` (Python, writes lifecycle histories to MinIO) and `build-minimum-payment-gateway` (Go Accounts, Payments, processor simulator and edge checkout). Issue #70 will later move fraud serving onto Knative with a KServe predictor.

## Goals / Non-Goals

**Goals:**

- One set of protobuf messages used by the generator, Payments, fraud and later DP1/streaming.
- A decision contract that stays valid when feature retrieval and KServe inference are added behind it.
- Remove the handbook model path completely rather than keeping it beside the new contract.

**Non-Goals:**

- Payments, Accounts or processor command RPCs (defined with their implementations in `build-minimum-payment-gateway`).
- Refunds, captures separate from sale, postings, webhooks and reconciliation events.
- Scenario/profile configuration schema (defined with the generator, its first consumer).
- Knative/KServe resources themselves (#70).

## Decisions

### Package layout and dependency direction

```
contracts/payments/v1/types.proto    Money, MerchantRef, CustomerRef, CheckoutSnapshot,
                                     LineItem, ShippingLocation, AttemptSignals, PaymentMethod
contracts/payments/v1/events.proto   PaymentEvent envelope + lifecycle payloads, RiskAssessment
contracts/fraud/v2/fraud.proto       FraudService.Decide  (imports payments/v1/types.proto)
contracts/labels/v1/labels.proto     FraudLabel           (no payments import; IDs only)
```

`payments.v1` events record the risk outcome in their own `RiskAssessment` message instead of embedding `fraud.v2` types. Go maps a proto package to one directory, so `payments` importing `fraud` while `fraud` imports `payments` would be an import cycle. Payments owns the recorded outcome anyway: replay consumes the recorded assessment, not the fraud response. Alternative considered: a shared `common/v1` package. Rejected because only one direction of reuse exists today.

### Version bump instead of in-place edit

The new decision contract changes semantics and field meanings, so it becomes `fraud.v2` and `fraud/v1` is deleted in the same change. Reusing `fraud.v1` would reuse field numbers with different types, which can silently misparse during a mixed rollout. No migration window is needed because there are no external callers, and the fraud service rolls forward alone.

### Raw attempt context, not features, in the decision request

The request carries identifiers, snapshot and signals. It does not carry precomputed features. Features are the fraud service's concern: today it uses only request fields, later it reads the online store (#56) and calls KServe (#70). Callers never change when features or models change. That is what lets the request stay fixed while Knative revisions and KServe canaries (#61) vary behavior, and why the response reports `policy_version`, `model_version`, `feature_set_version` so every recorded decision is attributable to a revision.

### KServe and Knative forward constraints

- The decision service remains the business gRPC boundary. Future inference uses KServe's Open Inference Protocol from inside the decision service. No custom inference proto is defined, so KServe runtimes can be used unchanged.
- Decisions are stateless per request, so Knative scaling and revision traffic splits cannot change outcomes for a given policy version.
- Readiness no longer waits for a model, which keeps cold start short. The synchronous path still keeps `min-scale` ≥ 1 per #70.
- A single gRPC port (8000) stays h2c-compatible for Knative. Metrics remain available on the separate pod port 8010; application scraping is deferred.
- Predictor-unavailable fallback (rules-only with a reason code versus failing closed) is decided with #56/#70, not here.

### Declines are responses, not errors

`fraud.v1` signalled rule rejections with `PERMISSION_DENIED`. Payments must record every decision as an event, so a decline is a normal `DECLINE` outcome with reason codes. Status codes are reserved for invalid input (`INVALID_ARGUMENT`), unavailability and internal failure.

### Rules-v1 uses only request fields

The handbook blocklists referenced synthetic handbook IDs and a 7-day average that no longer exists. `rules-v1` has two request-only rules: `HIGH_AMOUNT` (> 2,000.00 USD) mirrors the handbook's obvious sanity scenario, and `NEW_ACCOUNT_GEO_MISMATCH` (IP country ≠ shipping country, account < 7 days, amount > 200.00 USD) exercises the new signals. History-dependent patterns (card testing, velocity, reshipping) are left to features so the pipelines have something to prove. Thresholds are policy constants versioned by `policy_version`, not runtime configuration, so a version string always means one behavior. Only USD is supported because thresholds are currency-specific.

### Identifiers and privacy

IDs are opaque strings. Gateway-issued IDs are expected to be UUIDv7 (time-ordered, good for storage), but the contract does not require it. The snapshot keeps only a shipping address fingerprint, and signals keep an IP network fingerprint and IP country. Fingerprints are keyed hashes produced by the gateway; the key and algorithm belong to the edge/Payments implementation. Synthetic data uses dedicated integration IDs such as `synthetic-v1`.

### Labels separate chargebacks from simulation truth

Real labels arrive as chargebacks only for successful payments, which creates selection bias. Synthetic sources also know the truth for declined attempts. One `FraudLabel` message with a `source` enum (`CHARGEBACK`, `SIMULATION_TRUTH`) keeps both, lets training choose deliberately, and keeps `scenario` populated only for simulation truth.

### Sale semantics for the thin lifecycle

`PaymentSucceeded` means a combined authorize-and-capture sale. A separate capture, holds and refunds come later with #36/#58 as additive events. The lifecycle catalog lives in the `payment-contracts` spec and in proto comments. Executable golden histories arrive with the generator validator, their first consumer, and Payments reuses them.

### Fraud service simplification

Inference was CPU-bound native code, so it needed a thread pool with a capacity semaphore. Rule evaluation is microseconds of pure Python, so `Decide` evaluates inline in the async handler. The executor, `INFERENCE_WORKERS`, `MODEL_PATH`, `models/`, preprocessing, pandas, numpy, scikit-learn and hypothesis are removed. Pydantic stays for domain validation of the mapped request. The metrics are `fraud_decisions_total{outcome,reason}` (bounded labels) and `fraud_decision_latency_seconds`, replacing the prediction counters and score histogram.

### Edge becomes a health-only shell

With `/predict` removed, the edge has no gRPC client and no generated bindings. It keeps its composition root, config, correlation middleware and health endpoints, because `build-minimum-payment-gateway` adds checkout routes to it. `codegen:proto` generates Python bindings for all contracts into `src/fraud-service/gen/` and no Go bindings until Payments exists. The fraud service keeps its single rule evaluation in `app/domain`, protocol mapping in `app/transport`, and service-owned observability in `app/telemetry`; no pass-through application or empty storage layer is needed.

## Risks / Trade-offs

- [Rules-only decisions are weaker than the retired model] → The retired model was trained on credit-card handbook features that no ecommerce request can supply, so it was unusable anyway. The evidence page records the retirement explicitly.
- [Edge has no business route for two changes] → Acceptable: the edge is undeployed, and its checkout routes are planned next.
- [Contracts designed before Payments exists may need changes] → Scope is limited to fields the generator and fraud consume now. Additions are additive, and `build-minimum-payment-gateway` may extend packages with command RPCs.
- [USD-only policy] → Marketplace and synthetic data are USD. Other currencies fail validation visibly instead of being mis-thresholded.

## Migration Plan

1. Merge contracts, fraud service, edge, chart and docs together. CI builds both images.
2. Argo CD rolls the new fraud image in dev, then prod. No caller exists, so there is no ordering constraint.
3. Rollback: revert the merge commit. The old images and `fraud.v1` bindings return together.
